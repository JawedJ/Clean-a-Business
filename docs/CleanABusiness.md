# Clean a Business — Technical Specification

Reference doc for AI agents working on the codebase. Concise and technical.
Split into **what exists today** and **the design vision** it's building toward.

## Overview

Simulator-style Roblox game. Players clean businesses with tools (broom, pressure
washer, mop, vacuum) and continuously unlock more content — tools, businesses, upgrades, plot
expansions — as they progress.

- **Five cleanable kinds.** Four are tool-driven: **walls** (pressure washer — per-pixel
  `EditableImage` erase), **stains** (broom — server-timed scrub), **spills** (mop —
  client-driven Transparency fade), and **webs** (vacuum — server-timed removal, like stains).
  The fifth, **garbage**, is handled bare-handed: the player picks a piece up, carries it, and
  feeds it into the business's **shredder** (see *Garbage carrying* and *Garbage shredding*). Each
  kind is optional; a business declares whichever it authors, and the completion bar weights the
  kinds it has (see `CompletionWeights`). `gasStation` is the one business with garbage today.

- **6 players per server** (target), each with their own **plot** (a personal
  home/spawn base, assigned on join). Set by `CleaningConfig.PlotCount`. Each plot hosts a
  per-player **purchase progression** — step-on `Buttons` bought with **Cash** reveal
  `Spawnables` that generate **Gems** (see *Plot purchase progression*).
- Businesses are **shared buildings** in the world, not owned. Players take **jobs**
  from a job board: accepting a job teleports them to that business and lets them
  clean it. Cleaning is **per-session** — nothing about cleaned state is saved.
- **Jobs can be played together.** Up to 6 players form a **party** around one business, everybody
  **readies up**, and the whole party is teleported into **one shared session** — shared cleanables,
  one completion bar, and wall overlays kept in step by relaying erase strokes. See *Parties &
  shared jobs*.
- **Two currencies, two roles.** **Cash** (from jobs) buys plot buttons; **Gems** (generated by
  the spawnables those buttons reveal) buy the two permanent upgrade tracks — the **upgrades
  shop** (tools) and **skills** (+5%/level passives). So job → Cash → plot → Gems → power.
- Server is authoritative; clients read replicated data and send validated requests.

**Design imperative:** the set of unlockables (tools, businesses, upgrades) grows
indefinitely over the game's life. Every system must be data-driven and additive —
adding a new tool/business/unlockable should require new data + config, not rewrites.

---

# Current Implementation

What is actually built and running right now. The core loop is complete end to end — clean a
business for Cash + XP, spend Cash on the plot's buttons, spend the Gems those spawnables
generate on tool upgrades and skills — alongside job mastery, business/tool gating, and the
supporting HUD.

## Cleaning system (implemented)

### Verification policy (server-authoritative)
**No gameplay verification happens on the client.** Clients send *intent* (a click, a
target) and show *cosmetic* feedback; the **server validates everything and owns all
timing and completion**. The gate on every clean is the player's **active job** —
`JobService.getActiveJob(player)` must equal the `businessId` of the surface/stain they
report, so a player can only ever clean the one business they've accepted. Concretely:
- The broom's **UseTime timer runs on the server** (`DecalCleaningService`), not the
  client. The client only sends "I clicked this stain" and animates a progress bar; it
  cannot shortcut the timer or assert completion. The server also checks active job,
  hierarchy, broom-equipped, one-clean-at-a-time, and a per-session **already-cleaned
  set** so a stain can't pay out twice for the same player.
- Stains are **shared server instances**, so the server does **not** destroy a cleaned
  stain (that would remove it for everyone). It rewards the player and tells **their**
  client (`DecalCleaned` remote) to destroy the model locally; other players still see
  and can clean it independently.
- **Spills** (mop targets) are also shared server instances and cleaned **client-side** like
  walls — the mop fades a spill's Transparency to invisible at its own pace, then the client
  reports "this spill is fully mopped" via `CleanSpill`. The server can't witness the fade, so it
  re-validates the report against the active job, pays the per-spill reward, and records it in the
  `JobServer` (deduped — a replayed/forged report earns nothing and can't over-count). Nothing is
  destroyed server-side; the cleaning player's client hides its copy (`SpillVisibility`).
- **Two things clean entirely client-side: the wall EditableImage pixel-erasing and the mop's
  spill fade** — both inherently local (the wall overlay is built and erased on the client and
  never replicated; the spill fade is a per-client Transparency change — see Replication model).
  Walls grant only the per-second **wash reward** (`CleanProgress`), which the server re-validates
  against the active job and throttles per a cooldown; spills grant a **flat per-spill reward** on
  the single `CleanSpill` completion report (deduped). Neither can be farmed off a job the player
  doesn't hold.
  - The wash reward is the one that pays **silently** (`ProgressionService.rewardSilently`) — no
    `RewardPopup`, so no floating "+N XP! / +N Cash!" and no cash chime. Every other cleanable pays
    on a *discrete act* where a popup marks the moment; the wash pays every second the trigger is
    held, which as a stream of text over the crosshair is just noise. Walls are getting their own
    VFX in its place. The payout itself is unchanged.
- **Garbage is the exception to all of this, deliberately.** Because garbage *moves*, a shared
  instance would let two sessions drag each other's pieces around — so what a player carries is a
  **client-local clone**, and its position is never server state (see *Garbage carrying*). The
  server owns only **who holds which `surfaceId`, per session**, and relays the carrier's position
  to the rest of *their* party. Position is therefore client-trusted; that's acceptable while
  carrying pays nothing. The **act of cleaning** it — feeding it into the shredder — *is* validated
  and paid server-side like every other kind: the carry is presentation, the clean is authority
  (see *Garbage shredding*).
- **Completion is server-authoritative.** The player's `JobServer` counts the building's
  cleanables (walls, stains, spills, webs, **and garbage**) and only counts cleans the cleaning
  services have already validated (deduped), so the job completes — and pays its `BaseReward`
  (Cash) + `XpReward` (XP) bonus — exactly once, when every wall, stain, spill, web and piece of
  garbage is genuinely done. Webs are cleaned like stains (a server-timed vacuum click — see *Web
  cleaning*); garbage is cleaned by being shredded (`GarbageShredService` → `markGarbageCleaned`
  — see *Garbage shredding*).
- **Finishing early is a deliberate client/server hybrid.** The prorated finish-early payout
  needs the *partial* completion %, but wall pixel-erasing is client-only (unverifiable), so
  walls are **client-reported**: the client pushes its wall completion (`WallCompletion`
  remote, ~1/s while changing, plus a fresh value with `FinishEarly`) and the server trusts
  it, clamped to `[server-verified full walls, totalWalls]`. Stains, spills **and webs** stay
  server-authoritative (`cleanedDecalCount` / `cleanedSpillCount` / `cleanedWebCount` /
  `cleanedGarbageCount` — spills, webs and garbage only ever report at full completion, so there's
  no partial fraction to trust). So finish-early reward =
  `weighted(reportedWalls, cleanedStains, cleanedSpills, cleanedWebs, cleanedGarbage) / total × bonus`
  (per `CompletionWeights`),
  and it does **not** count as a completion. This is intentionally exploitable on the wall fraction
  — accepted so the payout can track the live % shown to the player. **Full** completion is
  unaffected: it still gates on the authoritative deduped counts only.
- **Nothing about cleaning is saved.** Jobs are per-session; the only persisted business
  data is the `Unlocked` flag (gates accepting a job) and the lifetime `Completions` tally
  (drives **job mastery** — see below).

### Surfaces
- A cleanable surface is any `BasePart` placed in a business's `CleanableWalls`
  folder, at this exact hierarchy:
  `Workspace.<BusinessesFolderName>.<businessId>.Cleanables.CleanableWalls.<part>`.
  - `businessId` is the **business folder's name** (e.g. `"mcDonalds"`).
  - `surfaceId` is the **wall part's name** (e.g. `"CleanableWall1"`), unique within
    the business.
  - `SurfaceResolver` (SharedModules) walks this hierarchy to derive the identity;
    no tags or attributes are needed. Anything outside this exact structure is ignored.
- The surface's part shows its normal "clean" look. A **dirt overlay** is layered on the
  face of the part's own **`Texture`** (whichever side the map author textured; falls back to
  the **Left** face if the part has no Texture) as a `Decal` whose `TextureContent` references a
  client-built `EditableImage`. Cleaning erases overlay pixels to reveal the part. The face's
  (u,v) pixel mapping and the brush-radius scaling both follow that same face choice.
- Businesses are authored **in the Studio place**, not in code (Workspace isn't
  Rojo-mounted) — a single shared `Workspace.Businesses` folder holds one building per
  `businessId`. The buildings are **shared by everyone**; the overlays layered on their
  walls are per-client.

### Plots & the job board
- **Plots** are the player's home base only. Each plot is a Folder (`Plot1..PlotN`) under
  the `Plots` folder in Workspace, with a `spawnPart`. `PlotService` (server) assigns each joining player a free plot,
  publishes its name via the `Plot` player attribute, spawns the character on the
  `spawnPart` (on assignment and **every** respawn), and frees it on leave. Plots no
  longer hold businesses, but they **do** host the per-player **purchase progression**
  (`Buttons` / `Spawnables`) — see *Plot purchase progression*. `PlotService` also exposes
  `onAssigned`/`onReleased` hooks that `PlotButtonService` uses to build/reset the plot.
- **Jobs** are how cleaning happens, modelled as a class on each side — one instance per
  active job. The job board UI (`JobUiController`) fires the `AcceptJob` remote with a
  `businessId`:
  - `JobService` (server manager) resolves **who the start covers** (the accepting player, or
    every member of their party — see *Parties & shared jobs*) and funnels it into the one
    `startJob(businessId, members)` path, checks each of them has
    `Unlocked` that business **and meets its `RequiredLevel`**
    (`BusinessConfig.RequiredLevel`, default 1), ends any job they're already on, creates a
    fresh **`JobServer`** session, publishes the `businessId` on each **`ActiveJob`** player
    attribute, and teleports every character onto the building's **`TeleportPart`**. One job at
    a time, per player. Exposes `getActiveJob`/`getJob` for the cleaning services to authorize +
    report cleans, and `getSessionMembers`/`getOtherMembers` for them to mirror a clean onto the
    rest of the session. The level gate is enforced here (server authority), not just by the
    hidden client button.
  - **`JobServer`** (class) is one **session**, covering one *or more* players (a solo player is
    a session of one). It is the authority on progress: it counts the business's cleanables from
    the shared building, records validated cleans (`markWallCleaned` / `markDecalCleaned` /
    `markSpillCleaned` / `markWebCleaned` / `markGarbageCleaned` — deduped **across the whole
    session**), and exposes
    `getCompletion`/`isComplete`. The *work* is shared — one set of cleaned cleanables, one
    completion percentage — while the *payout* is per member (own replay multiplier, own
    mastery/skill boosts, own `Completions` tally, own summary).
    When every wall, stain, spill, web and piece of garbage is done it pays **every member still on the session**
    the `BaseReward` (Cash) + `XpReward` (XP) **completion bonus** and calls back to `JobService`
    to end the job for each (clearing `ActiveJob`, which ends the state on the client).
    `finishEarly(player)` instead ends **one** member's run, paying a **prorated** share of that
    bonus for the fraction the *group* has cleaned and **without** counting a completion —
    everyone else keeps cleaning the same job with the same progress. Its wall fraction comes
    from `reportWallProgress` (client-reported, clamped, highest report on the session wins), its
    stain count from the authoritative server total (see the hybrid note above).
  - **Job mastery boost.** Both payouts scale their **XP** by the business's mastery
    multiplier (`Mastery.xpMultiplier`), read from the lifetime `Completions` **before** this
    run is tallied — so crossing a milestone rewards the *next* job, matching the boost the
    board already showed. Cash is unaffected. See *Job mastery* below.
  - **`JobClient`** (class), spun up by `JobController` when `ActiveJob` is set, builds the
    per-client wall **EditableImage overlays** (via the `SurfaceManager` engine) and tracks
    local completion for the UI. Completion is **smooth** — it sums each wall's live erased
    fraction (`SurfaceManager.getCleanedWallAmount`), so the bar moves mid-wall — and combines
    walls + stains + spills + webs + garbage through the shared **`CompletionWeights`** (same
    weighting the server uses), pushed to listeners via `JobController.onProgressChanged` on every
    stroke/clean. Stains, spills, webs and garbage each step whole
    (`cleanedDecals`/`cleanedSpills`/`cleanedWebs`/`cleanedGarbage`, fed in by `JobController`).
    Everything is deduped by the **shared instance** except garbage, whose instances are per-client
    clones — that one is deduped by `surfaceId`.
  - **`JobCompletionController`** (client) drives the completion HUD
    (`ScreenGui.JobCompletion`): a progress bar + `PercentageLabel` that fill from
    `JobClient`'s live completion, a `CurrentReward` label showing the Cash you'd bank by
    finishing now (`BaseReward × completion`, floored to match the server payout), and a
    **FinishEarly** button (mirrored by the **H** key) that fires the `FinishEarly` remote.
    Shown only while a job is active (off `ActiveJob`) — the counterpart to the board, which
    hides during a job.
  - **Stain visibility** is owned by **`DecalVisibility`** (client), driven by
    `JobController` off the same `ActiveJob` attribute. Stains are shared server instances,
    so this **hides every stain by default** (reparented off-world) and shows a business's
    stains **only while it's the active job** — a player never sees another business's (or
    an un-accepted business's) stains. **Spills** are handled the same way by the parallel
    **`SpillVisibility`** (also `JobController`-driven), which additionally resets each spill's
    Transparency on show for the redo (see *Spill cleaning*).
- **Completion ends the job; re-accepting reloads it (redo).** Because nothing is saved,
  accepting the same business again creates a brand-new `JobServer` (progress reset) and a
  new `JobClient` that rebuilds the overlays, `DecalVisibility` **un-hides** every stain, and
  `SpillVisibility` **restores** every spill to its authored Transparency (including ones cleaned
  or partly-mopped last run) — a fresh clean.
- The shared buildings and their `Cleanables` (`CleanableWalls` + `CleanableDecals` +
  `CleanableSpills`) are authored in the Workspace and already replicated, so accepting a job
  spawns nothing server-side. The only per-job "loading" is the client's overlays + stain/spill
  restore.

### Parties & shared jobs (implemented)
Play a job **with friends**: one job, one set of cleanables, one completion bar, several players.

- **A party** is 1..`PartyConfig.MaxSize` (**6**) players with one **leader**, formed **around one
  business**, owned by **`PartyService`** (server). The leader picks the job *first* — on the normal
  job board — and that `businessId` is fixed for the party's life, so a party always knows what it's
  going to play and the browser can show it. There are **no invites** — parties are **open**: the
  server pushes every client the list of joinable ones and a player joins the one they want. A party
  stops being joinable once it's **full** or once its members are **on a job** (the shared session,
  its progress and its teleport all happen at start time, so there's nothing coherent to drop a late
  joiner into). Symmetrically, **a player on a job can neither create nor join** a party — matching
  the UI, which isn't reachable during a job, and closing the hole where a mid-job joiner's own solo
  run would be ended without payout the moment the party started.
- **Joining is gated on the job.** A join is refused unless the joiner has the party's business
  Unlocked and meets its requirements (`BusinessService.canPlay` — the single server-side definition,
  shared with the accept path). Since the job refuses to start unless *every* member qualifies,
  letting an unqualified player in would silently wedge the whole party. The browser still **lists**
  those parties, with their requirements painted red — it just won't join them.
- **Leaving.** The leader leaving hands the party to the next member in join order; an emptied party
  is dissolved. **Kick** is leader-only and strictly "remove *someone else*" — a leader kicking
  themselves is refused, because leaving is `leave`'s job (and hands the party on rather than
  dissolving it). A kicked or departing member who's mid-job is **finished early** rather than
  losing the run, via the `onMemberRemoved` hook.
- **A member who stops playing the job stops being in the party.** Pressing **FinishEarly** removes
  them (`PartyService.leaveFor`, after the payout), and pressing **GoHome** on the summary does it
  again as a backstop. A party is a group about to play *one* job together, so a member who's done
  with it shouldn't hold the party closed to newcomers or get swept into the leader's replay.
  Completing the job disbands the party outright (below).
- **Membership is published twice**, for two different consumers: the **`PartyId`** /
  **`PartyLeader`** player *attributes* (server-set, so they replicate to **every** client — that's
  how any client answers "are these two in the same party?" without a snapshot), and the
  **`PartyUpdate`** remote carrying `{ party, available }` (the rich roster the UI renders; both
  fields always present, so `nil`/empty means *none*, never *unchanged*). The client mirror is
  **`PartyController`**, which also exposes `sharesParty(player)` / `hasCompany()` for the systems
  below. The roster payload carries the party's `businessId` and a **`ready` array parallel to
  `members`** (remotes only serialize string/number keys, so the server's player-keyed ready map
  can't go over as-is; `PartyController.isReady(party, member)` owns that indexing). Actions go back
  over **`PartyAction`** (`create` *(+businessId)* / `join` / `ready` / `leave` / `kick` / `disband`).
- **Starting a job.** Two ways in, both covering the **whole party**:
  1. **Everyone readies up.** `ready` is a toggle the server resolves; the last member to ready fires
     `PartyService.onAllReady`, which `JobService` turns into the start. There is no start button —
     this *is* the launch path, so nobody is dragged onto a run they didn't agree to. The flags are
     cleared before the hook fires, so a refused start (a member mid-respawn) leaves the party simply
     un-readied to try again, rather than wedged all-ready with nothing happening.
  2. **The leader's `AcceptJob`** — the board's Wash or the summary's **PlayAgain** — replaying the
     run the party already agreed to. A non-leader's `AcceptJob` is ignored.

  Either way the job is **all-or-nothing on entitlement** — refused unless **every** member passes
  `BusinessService.canPlay` (the party UI and the join gate keep unqualified players out in the first
  place; this is the server-side backstop). Every member is teleported in and put on the clock
  together.
- **Joinability is pushed, not inferred.** `JobService` calls **`PartyService.refreshJoinable()`** at
  the end of `startJob` and `endJob`, so a party closing to newcomers when it starts and reopening
  when its members finish is an *ordered* statement from the job layer. `PartyService`'s own
  `ActiveJob` attribute watcher remains as a backstop; both just recompute from live state, so the
  double call is harmless.
- **Shared cleaning.** All four *cleanable* kinds are deduped once per session, and the confirmation
  is mirrored to the whole session so the cleanable disappears on *everyone's* screen:
  `DecalCleaned` / `WebCleaned` are fired to every member (not just the cleaner), and spills — which
  are client-driven — add **`SpillCleaned`**, relayed to the *other* members after the mopper's own
  client has already hidden it. The per-clean Cash/XP stays with whoever did the work;
  `JobClient` counts each cleanable **once** (`_claim`), so a relay racing a local clean can't
  double-count the bar.
- **Shared garbage is a different shape**, because each member holds their **own clone** of a piece
  rather than one shared instance. What's mirrored is the carry: `GarbageCarry` tells the session who
  holds which `surfaceId` (so two members can't grab the same piece), and the carrier's `GarbageMove`
  stream drives the other members' copies. Nothing crosses to another session. See *Garbage
  carrying*.
- **Shared wall overlays.** Each client builds its own `EditableImage` per wall and the pixels never
  leave that client, so what's shared is the **strokes**, not the image: `PressureWasherController`
  queues every erase as `{ part, to, from?, radius }` and flushes the batch ~10×/s over
  **`WallStroke`**; `CleaningService` validates each entry against the sender's job and relays it to
  the other members; `JobController` replays it through `SurfaceManager.applyRemoteStroke`, which
  runs the identical `CleanableSurface:clean` the local washer would. Same starting dirt + same
  brush path = matching images, and because each client's own wall completion moves with it, so does
  the shared bar. Nothing is sent for a solo player (`PartyController.hasCompany`).
- **Finishing.** Full completion finishes **everyone** at once (each paid in full) and then
  **disbands the party** (`PartyService.disbandFor`, fired from the session's `onMemberFinished` when
  `isComplete()`): the group played what it formed around, so each of them is released to play again
  or go home on their own instead of staying silently queued together. One member pressing
  **FinishEarly** finishes **only them**, paid at the *group's* completion percentage, while the rest
  keep cleaning — and takes them out of the party (above). Leaving a party (by choice, kick, or
  disband) mid-job finishes that member the same way, via the `PartyService.onMemberRemoved` hook
  `JobService` registers. Disconnecting simply drops them from the session.
- **Seeing each other.** `JobGhostController` hides same-business players *except* your party
  members, who stay fully visible — the whole point of the mode. It reads `PartyId` through
  `PartyController`, and re-evaluates when either player's `PartyId` or `ActiveJob` changes.

#### Party UI (implemented)
Four authored frames, all owned by **`PartyUiController`** except the entry button. Everything is a
**view**: no local copy of the roster is kept — every button sends a `PartyAction` and the screens
redraw from the next `PartyUpdate`, so a refused action simply changes nothing.

- **`PlayTogetherFrame`** (`PlayTogetherController`) is the way in. It **toggles** the flow: it opens
  the party you're in, or the create/browse choice if you aren't, and pressing it again while any
  party screen is up closes that screen. It's shown exactly when the HUD clusters are — which it is
  *told*, via `JobUiController.onHudVisibilityChanged`, rather than re-deriving from `ActiveJob`.
  That matters because the HUD stays hidden through the finished job's summary until **GoHome**;
  deriving it locally brought the button back a screen early, over the summary. Still inert for the
  tutorial's duration.
- **`PartySelectionUI`** — create or browse. **CreatePartyBtn** *borrows the job board*
  (`JobUiController.openForSelection`): the next Wash press reports its `businessId` back instead of
  starting anything, and **that pick is what creates the party**, with the picker as leader. There's
  no second party job picker to keep in step with the board.
- **`PartyUI`** — the party you're in: `JobImg` (the business's art, read from the board's own
  `TaskDesign.BusinessImg`), `SelectedMapTxt`, `RewardsTxt` (the same line the board's rows show),
  ready-up, leave, and one `Player{n}` row per member showing `Name: READY / NOT READY` (rich text,
  so only the status is coloured). Kick buttons are the **leader's only** and never appear against
  the leader themselves.
- **`JoinPartyUI`** — one `PartySlot` per joinable party, cloned from the authored template: whose
  party it is, what it's playing, what that pays, and what it demands of *you*. Rebuilt in full on
  every server push (the list is short and changes on clicks, and rebuilding is what guarantees a
  party that filled up or started leaves the list under everyone looking at it). Join is offered only
  for parties you qualify for.
- **Motion.** Steps *inside* the flow (selection → board → room, selection → browser) are
  **instant** — `ExclusivePanels.openInstant`, so it reads as one window changing rather than three
  panels swooping past each other. Animation is reserved for entering and leaving: the HUD button's
  open, its press again to close, and the exit buttons.
- **A job starting takes the screen.** `JobUiController` calls **`ExclusivePanels.hideAll()`** the
  moment `ActiveJob` is set, snapping away *every* open panel rather than just the board. That
  matters most in a party, where the start is triggered by the last member's ready press — the others
  would otherwise be dropped into the business still looking at whatever they had up.
- **Shared requirement rendering.** The board's rows and the browser's slots ask the same questions of
  the same business, so the predicates *and* the painters live in one client module,
  **`BusinessGates`** (`canPlay`, `paintRequirements`, `paintRequiredItems`, `rewardsText`,
  `imageFor`, plus the `onChanged` list of data paths that can move any of them). It's what stops a
  row and a party for the same business disagreeing — or a Join button offering a party the job would
  then refuse.

### Plot purchase progression (implemented)
A per-player, per-plot **buy-and-unlock chain authored right on the plot** — the core progression
on the plot itself, distinct from the job/business unlocks. Owned by **`PlotButtonService`**
(server), built off `PlotService`'s assign/release hooks. This is a **core gameplay-loop system**:
Cash earned from jobs is spent here to unlock **Spawnables**, which in turn generate **Gems**.

- **Authoring (Studio, per plot).** Each `Plot(i)` holds two folders:
  - **`Buttons`** — purchase buttons named `Button1..ButtonN`. Each is a `Model` with attributes
    **`Cost`** (number, charged in **Cash**), **`UnlockID`** (string — the Spawnables Model it
    reveals), **`UnlockTwo`** (bool), a child `BasePart` named **`Interact`** (the step-on
    trigger), and optionally a billboard **`TextLabel`** (its price display).
  - **`Spawnables`** — one `Model` per `UnlockID` (what a button reveals). Optional **`GemRate`**
    number attribute = Gems/second it generates for the owner while unlocked.
- **The chain.** A fresh player sees only **`Button1`**; every other button and every spawnable
  starts hidden. When the plot **owner's** character steps on a visible button's `Interact` part,
  **if they can afford its `Cost` in Cash**, the server deducts the Cash, hides ("buys") that
  button, makes its `UnlockID` spawnable visible, and reveals the **next** button — or the **next
  two** if `UnlockTwo` is checked. A reveal **skips any button already bought** (tracked in the
  plot's runtime `bought` set, seeded on rebuild): with `UnlockTwo` layouts a lower button's
  `index+1` reveal can point at a neighbour bought out of order, and without this guard it would
  reappear. Not enough Cash → **nothing happens** (a 0.5s debounce lets a failed attempt be retried
  without spamming touches). Only the **owner** can trigger their own plot's buttons
  (`GetPlayerFromCharacter` == owner).
- **Persistence + plot reuse.** Purchases persist per player in **`DataTemplate.PlotButtonsBought`**
  (a `{ [buttonName]: true }` set). Plots are **shared and reused across owners**, so buttons are
  **never `Instance:Destroy()`'d** — "buying" a button just hides it. On the owner **leaving**, the
  plot is fully reset (everything hidden, connections dropped); when the **next** player is assigned
  that plot it is rebuilt from **their** save data. `replayFromSave` unlocks each bought button's
  spawnable and re-reveals the not-yet-bought frontier buttons (`Button1` is the baseline entry
  point). It's **layout-agnostic** — button/spawnable **names are identical across every plot**, so
  one saved set replays onto whichever plot the player is assigned.
- **Visibility engine.** `setVisible(model, visible)` toggles a whole Model: BaseParts
  (`Transparency`/`CanCollide`/`CanTouch`/`CanQuery`), `Decal`/`Texture`,
  particles/beams/trails/lights, **and `BillboardGui`/`SurfaceGui` `.Enabled`** (so a hidden
  button's billboard is hidden with it). Authored props are **snapshotted once** (`originalProps`,
  the first time each instance is seen) so a later hide can never overwrite the true values and
  restore is exact — critical because plots are hidden/shown repeatedly over the server's life.
  - **Authoring contract: plots are authored VISIBLE in Studio**, in their final, fully-bought
    resting state — that authored look *is* the definition of "shown". Authoring a part at
    `Transparency = 1` (or `CanCollide = false`) makes the snapshot record **that** as the
    restore target, so the part stays invisible/non-colliding forever, with no recovery path.
    What you see in the editor is the destination, not the starting state; the server hides it.
  - **Startup sweep.** `hideAllPlotsAtStartup` (run first in `PlotButtonService.init`) hides
    every plot at server start, **before any client can replicate it**. Without it plots stay
    visible from server start until the first owner's `onAssigned` — which **yields** on
    `waitForData` — so an early joiner would see every plot fully built for a moment. It also
    takes the authored snapshot at the one moment plots are guaranteed to still be authored-clean.
- **Spawn-in drop.** A **live purchase** drops its spawnable in over `SPAWN_ANIM_DURATION` (1s):
  it starts `SPAWN_ANIM_HEIGHT` (8) studs up and nearly transparent, then eases (Quad-out) down to
  its authored pivot and fades to its authored look (fade targets read from `originalProps`, never
  *less* transparent than authored). A **rebuild from save reveals instantly** (`animate = false`).
  Parts are non-colliding during the fall, so **`Hitbox`** parts reserve the landing footprint to
  keep a player standing there from being trapped; they're parented *outside* the model (so moving
  it doesn't drag them) and destroyed on landing or on a mid-drop cancel (plot reset).
  `makeLandingHitboxes` descends to each **leaf model** (one containing no Models of its own) and
  boxes it individually, plus one box per loose `BasePart` alongside sub-models — a single box over
  the whole spawnable would span the empty gap between sub-models that sit apart.
- **Price billboard.** Each button's `TextLabel` shows its **authored text plus a `" $<cost>"`
  price**, the cost run through **`NumberFormat.abbreviate`** (e.g. `$2.5k`, `$1.5m`). The price is
  drawn with **RichText** so only the amount is coloured — **green** when the owner can afford it,
  **red** when not (the affordability test uses the raw `cost`, so only the display is abbreviated). Repainted on build, after each purchase, and off the
  owner's live **`Cash`** changed signal, so the colour flips the instant their balance crosses a
  button's cost. Authored label text is captured once (`baseTextByLabel`) so rebuilds never stack
  the price onto an already-appended value.
- **Gem generation (worker + buff model).** A single **1 Hz** loop
  (`computeGemsPerSecond`) awards **Gems** to the owner via `ProgressionService.awardGems`;
  fractional totals carry over (`gemAccum`) so sub-1/s income still eventually pays out.
  - **Workers** are the base generators: `CleaningConfig.PlotWorkerSpawnables` (`Car1`, `Car2`)
    — identified by **name** (case-sensitive; must match the Spawnable Model names exactly),
    carrying **no attributes** — each contribute `PlotWorkerBaseGemRate` (**1**/s) to the base.
  - **Buffs** are every other unlocked spawnable, applied to **each** worker: `BaseAdd`
    adds flat Gems/s to a worker's base, `BaseMultiplier` scales it (stacking multiplicatively).
  - Per plot: `perWorker = (PlotWorkerBaseGemRate + Σ flat) × Π multiplier`, and
    `gems/s = perWorker × activeWorkerCount` (+ any standalone `GemRate` generators, which live
    outside the worker model). With no workers unlocked, buffs scale nothing.
- **Hooks + races.** `PlotService` exposes `onAssigned`/`onReleased(fn)`, registered by
  `PlotButtonService.init` **before** `PlotService.init` so the join sweep builds each plot (and
  after its own startup hide sweep, so no plot is ever assignable while still visible). A
  per-plot **generation token** (`plotGen`) makes an in-flight build (which yields on `waitForData`)
  bail if the plot was reassigned while it waited, so a plot is never painted for the wrong owner.

### Business unlocking (implemented)
Businesses live in the **`BusinessConfig`** catalog and are **unlocked per player**, resolved
server-side by **`BusinessService`**:
- Every business starts **locked** (`DataTemplate.BusinessList` seeds all with `Unlocked =
  false`). DataService reconcile only fills template-defined keys, so the template lists **one
  entry per catalog business** to keep them all present on every profile.
- On join (after `waitForData`), `BusinessService.resolve()` seeds any still-missing catalog
  business into the profile (locked) and then **grants** any whose requirements are met.
  **Requirements today = `RequiredLevel`** (`meetsRequirements`), the single spot to extend for
  future gates (e.g. an owned tool). Resolution is **one-way — it only ever unlocks, never
  revokes** — so a business stays unlocked forever once earned.
- Resolution **re-runs on every `Level` change**, so reaching a business's `RequiredLevel`
  unlocks it live; the client board refreshes off the `BusinessList` changed signal.
- The job board row (`JobUiController`) shows the **`WashButton`** only when the business is
  `Unlocked` **and** the player meets `RequiredLevel`, otherwise the **`LockedButton`**. Its
  **`Requirements`** label reads `REQUIRED: Level N` and turns **green** once the level is met
  (red-orange while short).

### Job mastery (implemented)
Per-business progression driven off the lifetime `Completions`, shared by client + server via
the **`Mastery`** module so payout and display can't drift:
- **Stars (0→5).** One star per milestone. Tier N asks for `STEP × N` completions **within its
  tier** (`STEP = 5`), so the cumulative thresholds are **5, 15, 30, 50, 75**. The board shows
  progress relative to the current tier (it "resets" to `(0/req)` after each star); the real
  `Completions` count never resets.
- **XP boost (linear).** Each star adds a flat 5% of the base to the completion's XP:
  multiplier `1 + BOOST*stars` (`BOOST = 0.05`) → +5%, +10%, +15%, +20%, +25%. Applied to full
  completions **and** finish-early payouts (see `JobServer`). Cash is never boosted.
- **Board display** (`JobUiController` per row): `StarAmount` = one ⭐ per star; the `Rewards`
  line's XP figure is rewritten to the boosted value; `MasteryRequirements` shows the next
  star's completion goal, tier progress, and the **total** boost that star grants (cumulative,
  e.g. the 2nd star reads `+10%`): `Achieve 100% N times to Unlock: +X% EXP (progress/N)`, and
  hides once all 5 stars are earned.

### Skills (implemented)
**Gem-purchased passive boosts**, bought level-by-level and permanent once bought. This is the
main **Gem sink** (jobs earn Cash → plot buttons buy Spawnables → Spawnables generate Gems →
Gems buy skills). All price/cap/effect math lives in the shared **`SkillsConfig`** so the
client's display and the server's authority can't disagree; **`SkillsService`** (server) owns the
writes and **`SkillsUiController`** (client) draws the panel.

- **The catalog.** Five skills, keyed by the **`SkillName`** attribute authored on each Skill
  `ImageLabel`. Every level adds `effectPerLevel` (**+5%** for all five) to a **1.0 base**, so
  level *L* gives multiplier `1 + 0.05 × L`. Cap is **`MAX_LEVEL = 5`** (+25% fully bought):

  | Skill | Boosts | Applied by |
  | --- | --- | --- |
  | `RadiusMaster` | cleaning brush radius | `PressureWasherController` (**client-side**) |
  | `Speedy` | walk speed | `SkillsService` (free-roam) + `JobServer` (on-job) |
  | `Inteligence` | XP gain | `ProgressionService.awardXp` |
  | `Greed` | Cash gain | `ProgressionService.awardCash` |
  | `Hoarding` | Gem gain | `ProgressionService.awardGems` |

  (`Inteligence` is spelled that way in code and data — it's the attribute key, so don't "fix" it
  without migrating saved profiles.)
- **Pricing.** The next level costs `floor(BASE_PRICE × GROWTH ^ level)` Gems, with
  **`BASE_PRICE = 100,000`** and **`GROWTH = 2`** — so the first level of *every* skill costs
  100k and each further level doubles.
- **Read point.** `SkillsService.getMultiplier(player, skillName)` is the single place server
  systems read a skill's strength from; it returns **1.0** for an unknown skill or unset level, so
  callers can multiply unconditionally. The client reads levels straight from replicated data and
  calls `SkillsConfig.multiplier` itself (see `PressureWasherController`, and `JobUiController`'s
  reward preview).
- **Buying.** `PurchaseSkill(skillName)` (client → server). The client predicts affordability to
  pick the SFX (`Purchase` vs `PurchaseFailed`) and fires; **`SkillsService.onPurchase`
  re-validates everything** — real skill name, below cap, can afford `getCost(level)` — then
  deducts Gems and bumps the level. The two `DataService:update` calls can't half-apply: the server
  handles one remote event at a time and neither call yields. Buying **`Speedy`** additionally
  calls `refreshWalkSpeed` so movement changes immediately rather than on the next respawn.
- **Robux "unlock all".** `UnlockAllButton` prompts dev product **`3609731896`**, granted in
  `SkillsService.processReceipt` by setting every skill to `MAX_LEVEL`. The grant is
  **idempotent** (writing the cap over an already-maxed skill changes nothing), so a re-processed
  receipt can never over-grant; it returns `NotProcessedYet` on failure so Roblox retries. The
  button **hides once every skill is maxed** — the product would grant nothing, so it must not be
  sellable. **Note:** only one `ProcessReceipt` callback exists per game and this module sets it;
  a second product must be routed through a shared dispatcher rather than overwriting it.
- **Panel display** (`SkillsUiController`, one row per skill): `GemAmt` shows the **next** level's
  price as `💎<abbrev>` (tinted pink when affordable, red when not — via a `UIGradient`, because a
  RichText `TextColor` won't tint the emoji), or **`MAXED`** at the cap; `Circle1..Circle5` fill
  yellow one per level bought (authored colours captured per bind so unfilled pips restore the
  designer's colour). Repaints off the replicated `Skills`/`Gems` change, so the panel never trusts
  its own optimism.

### Upgrades shop (implemented)
**`ShopService`** (server) + **`UpgradesUiController`** (client), also priced in **Gems**. Two
actions, both re-validated server-side:
- **`PurchaseItem(uniqueId)`** — unlock a not-yet-owned tool: charge its `ToolConfig` `Cost` and
  add it to `Inventory` (`Unlocked`, `Level 0`). `ToolService` picks the new inventory entry up and
  grants the physical `Tool`.
- **`UpgradeItem(uniqueId)`** — level an owned tool up by one, charging the cost and applying that
  item's per-level stat steps.

All upgrade math lives in the shared **`ItemUpgrades`** module: cap **`MAX_LEVEL = 10`**, cost
`floor(BaseUpgradeCost × GROWTH ^ level)` with **`GROWTH = 2.3`** (per-item base, shared curve).
`applyUpgrade` is **pure** (clones the item) and only steps a stat the item actually has — a broom
has no `Radius`. `UseTime` steps *down* (faster) with a **`MIN_USE_TIME = 0.1`** floor so it can
never reach zero or go negative.

### Robux store (implemented)
**`ShopProductsService`** (server) + **`ShopUiController`** (client) — `ScreenGui.ShopUI`, toggled
from `HUD.AllButtons.Buttons2.StoreButton` through the shared `ExclusivePanels` coordinator like
every other board. Every label on the offers is authored static, so the controller **paints
nothing**: it only wires each `ScrollingFrame` offer frame's `BuyBtn`, coupling that button's hover
grow to the sibling `PriceTxt_STATIC` so the price grows with it.

`ScreenGui.ShopAlternateBtn` is a second, standalone entry point that toggles the same panel. It
exists to sell the **starter pack**, so it hides once that pack has nothing left to give — the same
condition that stops its click from prompting, so it can never be a dead end — and during a job
(nothing else hides it, as it sits outside the HUD clusters).

The catalog is the shared **`ShopProducts`** module, keyed by the offer frame's **name**
(`25kCashFrame`, `SpeedFrame`, …): flat cash/gem packs, the permanent **2x Cash** / **2x Gems**
multipliers, a permanent **+12 walk speed**, the **starter pack** (unlock every tool and max each
one's upgrade level), and the **skills pack** (the SkillsDisplay's own "unlock all" product).

- **Two kinds of purchase.** The cash/gem packs, the speed perk and the skills pack are **developer
  products**; the 2x multipliers (`1941048632`) and the starter pack (`1943706546`) are
  **gamepasses**. Each id is listed in exactly one of `DevProductFallbacks` / `GamePasses`, and that
  membership decides which prompt the client raises (the wrong one just errors) and how the server
  delivers it.
- **Dev products: several offers share one id** (25k cash and 25k gems are both `3644862015`), so
  the receipt alone can't say what to grant. The client fires the frame name over **`ShopIntent`**
  just before prompting; the server stores it **keyed by product id** (so two different products'
  intents can't shadow each other) and the receipt grants it. An intent lost to a restart falls back
  to `DevProductFallbacks[productId]` rather than swallowing the purchase. A forged frame name can
  only ever redirect a purchase of the product that frame actually sells.
- **Gamepasses have no receipt** — ownership is one permanent boolean, so the grant is re-derived
  from it in **two** places: `PromptGamePassPurchaseFinished` (lands the perk at once) and a **join
  sweep** (`UserOwnsGamePassAsync` per pass), which also covers a pass bought on the website, one
  bought while the server was down, and every session after the first. A failed ownership check is
  warned and **skipped**, never treated as "doesn't own it". This only works because every grant is
  idempotent. An intent can't be used here (a player who bought via one frame could never re-prompt
  from the other), so a pass grants the **union** of every offer sold on it — two frames on one pass
  are two shop-fronts for the same purchase.
- **`SkillsPackFrame` is granted elsewhere.** Only one `ProcessReceipt` handler may exist per
  product, and `SkillsService` already owns `3609731896`; the store just prompts it. It is absent
  from both lists — `DevProductFallbacks` doubles as the list of products `ShopProductsService`
  registers receipt handlers for.
- **Currency packs are credited raw**, not through `ProgressionService` — a paid 100k pack must pay
  exactly 100k, not 100k inflated by the buyer's `Greed`/`Hoarding` or by the 2x perk the same store
  sold them. Same reasoning as `GemProductsService`'s claim.
- **Permanent perks live in `DataTemplate.ShopBoosts`** and are read through **`ShopPerks`**, a
  DataService-only leaf module so `ProgressionService`, `SkillsService`, and `JobServer` can apply
  them without pulling in the purchase pipeline. Every grant is an **"at least this much" write**,
  never an accumulate, so a re-delivered receipt can't stack a perk.
- **Walk speed** adds the bonus **after** the `Speedy` multiplier (`base × Speedy + SpeedBonus`) in
  both places speed is set — free-roam (`SkillsService.applyWalkSpeed`) and pinned on the job
  (`JobServer._pinWalkSpeed`) — so +12 is worth exactly +12, on or off the clock. The grant calls
  `refreshWalkSpeed` so it lands without a respawn.
- A click **refuses to prompt** when the offer would grant nothing (perk already owned, all skills
  maxed, all tools unlocked and maxed). The grants are idempotent regardless; this is about never
  taking Robux for a no-op.

### Settings (implemented)
**`SettingsService`** (server) + **`SettingsUiController`** (client), persisted under
`DataTemplate.Settings`. The client applies changes **locally for instant feedback**, but a
client's own DataService writes neither replicate nor save — so to *remember* a setting the client
fires **`UpdateSetting(key, value)`** on release and the server re-validates and writes it through
DataService, which persists it and replicates the confirmed value back.

Only known keys are accepted, each coerced by a **sanitizer** before saving, so a client can't
stuff an arbitrary key or a wrong-typed/out-of-range value into its profile: `MusicVolume` /
`SFXVolume` must be a real number (NaN rejected via `value == value`) clamped to `0..1`;
`HidePlayers` must be a boolean.

### Company panel (implemented)
**`CompanyUiController`** (client) + **`CompanyService`** (server) — the player's business-at-a-glance
panel (`ScreenGui.CompanyUI`), opened from `HUD.AllButtons.Buttons2.CompanyButton`.
- **Toggle.** The `CompanyButton` toggles the panel through **`ExclusivePanels`** (registered under
  `"Company"`), exactly like the board/shop/skills/settings — so **at most one panel is open at a
  time**: opening this closes whichever of those was up, both animating together with the shared
  **`UiAnimations.Panel`** motion (slide-up+expand / swoop-down+shrink). The `ExitButton` calls
  `ExclusivePanels.close`. The coordinator owns all the mid-animation gating + queueing; the
  `beforeOpen` hook refreshes the live labels right before the panel springs in.
- **`MainFrame`** (an `ImageLabel`) holds everything, split into `TopSubframe` / `BottomSubframe`.
  `TopSubframe` is what's wired today:
  - `ImageCard.ImageLabel` — the local player's **avatar headshot**, fetched async via
    `Players:GetUserThumbnailAsync` (spawned + pcall'd; a failure leaves the authored placeholder).
  - `InfoCard.PlayerInfoText` — `"<DisplayName>'s Business"`.
  - `InfoCard.StarsAmtText` — the player's **average per-job star rating**, `Ratings.Sum / Count`
    (the **1-star floor** before any job is rated), rendered as a row of **⭐ emoji** (the average
    rounded to the nearest whole star, 1..5 — like the JobSummary screen) and kept live off the
    `Ratings` changed signals.
  - `InfoCard.DescriptionEditableTxt` (a `TextBox`) — an editable description the player writes.
    Persisted across sessions exactly like the settings: the box edits locally, and on **focus-lost**
    the client fires **`UpdateBusinessDescription`**; `CompanyService` coerces to a string, **trims**,
    **caps at 200 chars**, and writes `DataTemplate.BusinessDescription` via DataService, which
    replicates the confirmed value back (re-applied unless the box is mid-edit). Empty saved value ->
    the box shows its placeholder.
- **Per-job star rating (`Ratings`).** A job's rating is `JobRating.starsFor(fraction)` — one star per
  20% cleaned, clamped 1..5 (full completion = 5). `JobServer._fireSummary` folds it into the running
  `Ratings` tally (`Sum` += stars, `Count` += 1) on **every** job end — full completion **and**
  finish-early alike — so the panel's average covers all jobs. The **same** `JobRating` module draws
  the star on the JobSummary screen, so the shown and banked ratings can't drift (like `Mastery`).
  This is **distinct from job mastery**: mastery stars come from lifetime `Completions` per business;
  the Company rating is a global average of finish quality.

**UI convention — every panel opens/closes with `UiAnimations.Panel`.** All full-panel frames in
the game (job board, upgrades shop, skills, settings, Company, and any panel added later) show and
hide through the shared **`UiAnimations.Panel`** (`:open()` / `:close()` / `:hideInstant()`), never
by toggling `Visible` directly — that shared spring-up/expand + swoop-down/shrink motion is the
game's consistent panel feel. Build one per frame on each bind (`Panel.new(frame)`, off the frame's
authored resting geometry). The norm is to register the panel with **`ExclusivePanels`** and drive
open/close through the coordinator (`ExclusivePanels.toggle`/`.close`/`.open`) rather than calling
`panel:open()`/`:close()` directly — that enforces **one panel open at a time** (opening one closes
whichever was up, both animating together) and owns all the mid-animation gating + queueing. The
board, shop, skills, settings, and Company panels all do this. **Never** open/close a panel by
setting `.Visible` alone.

**UI authoring convention — `_STATIC` labels.** Any `TextLabel` whose name ends in **`_STATIC`**
(e.g. `RatingText_STATIC`, `EarningsTxt_STATIC`) is designer-authored copy and is **never read or
written in code** — leave its text alone. Only the non-`_STATIC` value labels are code-driven.

### Tutorial resume (implemented)
The onboarding run **survives disconnection**. `TutorialService` persists the current step on every
change (`DataTemplate.TutorialStep`) and writes `TutorialComplete` only when the **last step ends**,
so a player who leaves halfway picks up where they left off instead of forfeiting the tutorial.

Where they pick up is `TutorialConfig.resumeStep`, which lives next to the step table because it's
derived from it — reordering or inserting steps keeps the rules right. Usually it's the same step,
with two exceptions for steps that assume a world state a fresh join doesn't have:

- **A step ending on `JobDone`** (step 9, *CleanJob*). The job doesn't survive the disconnect and a
  respawn always returns the player to their plot, so the step could never end on its own trigger —
  it would strand them. They were doing the job when they dropped, so it counts as **done** and they
  resume on the step after it (→ 10).
- **A step running with a panel already open** — it names a `panel` but isn't the step that opens it
  (steps 8 and 11). Nothing is open on a fresh join, so its highlight would point at a panel that
  isn't there; they go **back a step**, to before the panel was involved, and are walked to it again.
  Where an explicit "go and open it" step exists — the nearest earlier step on the **same panel**
  ending on `BoardOpen` — that's the one (8 → 7). Otherwise it's simply the preceding step, whose own
  ending re-delivers this one cleanly (11 → 10, since the shop is opened *and* used within step 11).

**Locks need no special handling on resume.** Every restriction is a function of the current step and
nothing else — the server gates (`canPurchasePlotButton` / `canPurchaseTool` / `canUpgradeTool`) read
it live, and the client's come from `applyRestrictions` off the step attribute — so *entering* the
step is what re-arms them. The plot matches too: `replayFromSave` rebuilds its reveal state from
`PlotButtonsBought`, so a resumed step sees exactly the plot it left. Entering a step as a resume is
**not** reported to the Onboarding funnel; it isn't forward progress, and a backward resume would
otherwise re-report an earlier step.

**Skipping.** Any player may type **`/skiptutorial`** (parsed in `AdminCommands` alongside the
owner-only dev commands, but ungated). It calls `TutorialService.skip`, which runs the same `finish`
path reaching the last step does: the profile is marked `TutorialComplete` (so it never runs again),
the resume point goes back to 0, and clearing the `Active`/`Step` attributes is what makes the client
drop every UI lock the current step had armed. The remaining **funnel steps are deliberately not
logged** — they didn't reach them, and reporting them would make the Onboarding funnel read as a
completion.

`TutorialComplete` previously meant "has been offered the tutorial", written at the *first* step.
Players carrying that older `true` still skip — which is what they'd have got anyway — but one who
abandoned a run back then has no step recorded to resume from, so they stay skipped.

### Analytics funnels (implemented)
**`FunnelService`** (server) — two **progression** funnels via `AnalyticsService:LogFunnelStepEvent`,
kept apart from the systems they watch so each is just a listener plus a step number. (The tutorial's
**Onboarding** funnel is separate — it uses `LogOnboardingFunnelStepEvent`, the single per-experience
funnel, and lives in `TutorialService`.)

- **`PlotCompletion`** — 10 steps, one per 10% of the player's plot purchase buttons bought
  (`"10% Plot Complete"` … `"100% Plot Complete"`). Driven off `PlotButtonService.onPurchased`, the
  only thing that moves plot completion, with the bought/total pair read from the player's **live
  plot state** via `getPlotProgress` so the denominator is the plot as actually built. A plotless
  player reports nothing.
- **`JobsUnlocked`** — one step per business unlocked (`"1 Job Unlocked"`, `"2 Jobs Unlocked"`, …).
  Driven off the player's **`BusinessList` changing**, which is where `BusinessService`'s unlocks
  land — so it needs no hook of its own and catches an unlock however it was earned (level-up, tool
  purchase, or the join-time resolve). The count is **recomputed from the profile**, never tracked
  incrementally, so it can't drift.

Both are **lifetime** funnels spanning every session, which drives two decisions: the
`funnelSessionId` is the player's **UserId** (a per-session id would restart the funnel each join,
reading as pure drop-off), and the highest step reported is **persisted**
(`DataTemplate.FunnelProgress`) so a rejoin can't re-report old steps. Steps are always reported
**contiguously** — advancing to step N reports every step from the stored mark + 1 up to N — which
covers both a jump past a threshold and, once, a player who was already mid-progression when the
funnels were added. The mark is written only **after** the reports, so a throw retries rather than
skipping a step. Every write is best-effort inside a `pcall`: analytics are unavailable in Studio,
and a funnel write must never take a purchase or an unlock down with it.

### `CleanableSurface` (client OOP class)
One instance per cleanable part. Owns the dirt overlay and the erase logic.
- **Shared dirt template:** the initial dirt image is identical for every surface, so
  it's drawn + read back + pixel-counted **exactly once** (`getTemplate`, lazily on the
  first surface; the dirt asset downloads on that call). Each surface then just
  **`buffer.copy`s** that template into its own working buffer and does **one**
  `WritePixelsBuffer` to seed its `EditableImage`. No per-surface `DrawImage`,
  `ReadPixelsBuffer`, or counting loop.
- **Performance contract (the whole reason past attempts went choppy):** the pixels
  live in **one persistent `buffer`** per surface. Erasing mutates that buffer **in
  place** and does a **single `WritePixelsBuffer` per frame**. There is **zero
  per-frame heap allocation**, so there's no GC churn that builds up over time —
  cleaning cost is constant, not growing. Do **not** reintroduce per-frame
  `ReadPixelsBuffer`/buffer allocation.
- `clean(worldPos, fromWorldPos?)`: maps the world hit point to a pixel coord on the
  left face, erases a **circular stamp** (a world-space circle → ellipse in pixel
  space on non-square parts), and **interpolates stamps along the segment** from the
  previous point so fast strokes leave no gaps.
- **Completion:** when erased fraction ≥ the surface's threshold, it marks itself cleaned,
  destroys the decal, and fires its `onCleaned` callback. The threshold defaults to
  `CompletionThreshold` (0.975) but a wall can override it with a numeric **`Percentage`**
  attribute (a 0–1 fraction like `0.9`, or a 0–100 percentage like `90`; values > 1 are read as
  a percentage) — resolved per-surface at construct time. It also fires `onProgress` on any
  stroke that erased pixels, so the completion bar tracks the wash live rather than only stepping
  when a whole wall finishes.
- **`setGlow(enabled)`** toggles the reveal glow **on the wall's own dirt decal** (no second
  decal — two coplanar decals z-fought and rendered unreliably). On enable it recolors the
  still-dirty pixels toward neon yellow into a `glowBuffer` (the real dirt in `self.pixels` is
  left untouched) and uploads that; `stamp` zeros its alpha in step with the dirt so the glow
  shrinks with the wash at no extra per-stroke cost. On disable, on wall completion, and in
  `destroy` the plain dirt is re-uploaded and the buffer dropped (see *Reveal remaining
  cleanables*).

### `PressureWasherController` (client)
- Detects the tool via the `ToolId` attribute and binds its `Equipped` / `Activated`
  (hold to fire) / `Deactivated` / `Unequipped` events. **No ammo** — firing is
  unrestricted while held.
- **Mobile (touch-only devices):** holding to fire while dragging to look is impossible, so
  on mobile the washer fires **continuously the whole time it's equipped** (`Activated` /
  `Deactivated` are ignored; only `Unequipped` stops it). Desktop and console (gamepad) keep
  the normal hold-to-fire. `IS_MOBILE` = `TouchEnabled and not Keyboard/Mouse/Gamepad`.
- Each `Heartbeat` while firing: raycasts and, if it hits a cleanable part **on its overlay
  face** (the hit normal must match the surface's own face within `> 0.99`), tells that surface
  to clean. The ray also **ignores each business's `Interior` and `CleanableDecals` folders** (so
  props/windows and stain hitboxes in front of a wall don't block the wash). Tracks the last hit
  so consecutive frames bridge into one stroke. The aim point is the **mouse** on desktop
  but the **center of the screen** (`ViewportSize/2`, the crosshair) on mobile — since the
  mobile washer fires from the crosshair, not from wherever the player last tapped.

### `SurfaceManager` (client) — wall-overlay engine
- A driven engine, not a decision-maker: `JobClient` calls `buildWalls(wallsFolder,
  onCleaned, onProgress?)` to start tracking the current job's walls and `clear()` to tear
  them down. It builds/destroys one `CleanableSurface` per wall (handling walls that
  stream/replicate in via `ChildAdded`).
- **Budgeted building:** walls are queued (after a cheap resolve check) and a long-lived
  drainer builds them under a per-frame time budget (`FRAME_BUDGET`, ~2ms), so a job with
  many walls never stalls a frame. `removeSurface`/`clear` cancel still-queued walls.
- Exposes `getSurface(part)` for `PressureWasherController` and `getCleanedWallAmount()`
  (summed live wall fractions, in whole-wall units) for the completion bar. On completion it
  plays the pop VFX + sound and invokes the `onCleaned` callback (which `JobClient` uses to
  fire `WallCleaned`); every dirt-removing stroke invokes `onProgress`, which drives the bar.
- `setWallsGlow(enabled)` fans the reveal glow out to every built wall (calls each surface's
  `setGlow`), used by `MissingHighlightController` (see *Reveal remaining cleanables*). The flip
  is **budgeted across frames** by a `processGlow` drainer (like the build queue) — toggling the
  glow is a full-image recolor + upload per wall, so applying it to a whole job at once hitched;
  now a few walls flip per frame (`GLOW_FRAME_BUDGET`) in a fast wave.

### Persistence
**Cleaning is not persisted.** Jobs are per-session: accepting a job is always a fresh
clean, and nothing about cleaned walls/stains is written to DataService. The business data
saved per player is the **`Unlocked`** flag (gates accepting a job, resolved by
`BusinessService`) and the lifetime **`Completions`** tally (drives job mastery).

the folder names `BusinessesFolderName`/`CleanablesFolderName`/`WallsFolderName`/
`DecalsFolderName`/`SpillsFolderName`/`WebsFolderName`/`GarbageFolderName`/`InteriorFolderName`
(props/windows the cleaning ray ignores), `HitboxName`/`SurfaceIdAttribute` (stains/walls, and also
the web id) + `SpillSurfaceIdAttribute`/`GarbageSurfaceIdAttribute` (the capital-S spill and garbage

the outline can be pulled in independently) / `GarbageCarryDistance` (7, how far out front a held

`ShredderModelName`/`ShredderHitboxName`/`ShredderEntryPartName`/`ShredderExitPartName` and its three
animation beats `GarbageShredEntrySeconds` (0.3) / `GarbageShredHoldSeconds` (0.45) /
`GarbageShredDropSeconds` (2) — shared because the server waits out the same total before counting
the piece — plus `ShredderSoundName` and `GarbageShredSoundLeadSeconds` (0.3, how far into the hold
the SFX starts ahead of the drop), `PlotCount`/`PlotAttribute`/

`PlotButtonCostAttribute`/`PlotButtonUnlockIdAttribute`/`PlotButtonUnlockTwoAttribute`, the
gem-income config `PlotWorkerSpawnables`/`PlotWorkerBaseGemRate` and the spawnable buff/generator
attributes `PlotSpawnableGemFlatAttribute`/`PlotSpawnableGemMultiplierAttribute`/
`PlotSpawnableGemRateAttribute`, `ActiveJobAttribute`, `TeleportPartName`/`TeleportOffset`,
`DirtAsset`, `ImageSize`, `BrushWorldRadius`, `MaxBridgeWorldDistance`,
`CompletionThreshold`, the completion-bar weights `DefaultDecalWeight`/`DefaultSpillWeight`/

### Stain cleaning (broom, implemented)
- A cleanable **stain** is a `Model` in a business's `CleanableDecals` folder, at:
  `Workspace.<BusinessesFolderName>.<businessId>.Cleanables.CleanableDecals.<model>`.
  - The model has a child `BasePart` named **`Hitbox`** (what the player clicks) and a
    **`surfaceId`** attribute whose value is the stain's id (unique within the business).
  - `DecalResolver` (SharedModules) walks this hierarchy + reads the attribute to derive
    `{ businessId, surfaceId, model }`; anything else is ignored.
- **Flow:** `BroomController` (client) raycasts on click, and on a valid Hitbox (for the
  business whose job it holds) fires `CleanDecal` and shows a cosmetic billboard progress
  bar. `DecalCleaningService` (server) validates (active job / equipped / one-at-a-time /
  not-already-cleaned-on-this-job), then **runs the UseTime timer itself**, re-validates,
  rewards the player, records the stain in the player's **`JobServer`** (which may complete
  the job), and fires `DecalCleaned` back to **that** client. The stain model is **shared
  and left intact server-side**; the cleaning player's client **hides** its copy via
  `DecalVisibility` (which already keeps stains hidden unless you're on the job), and
  re-accepting restores it for the redo. **UseTime** comes from the broom Item in
  `ToolConfig`; both sides read the same source so the bar mirrors the server timer.
- **Cleaned-stain tracking lives in the `JobServer`**, so it resets on each accept — the
  player can redo the job and earn the rewards again.

### Spill cleaning (mop, implemented)
The **third** cleanable kind, alongside walls and stains. A spill is cleaned like a **wall**
(client-driven, continuous), not like a stain (server timer) — the mop fades the spill out over
time rather than clicking it once.
- A cleanable **spill** is a `Model` in a business's `CleanableSpills` folder, at:
  `Workspace.<BusinessesFolderName>.<businessId>.Cleanables.CleanableSpills.<model>`.
  - The model carries a **`SurfaceId`** attribute (capital-S — that's how the spill models are
    authored in Studio, distinct from the stains'/walls' lowercase `surfaceId`) whose value is
    the spill's id (unique within the business; a number is accepted and normalised to a string).
  - Unlike a stain it has **no required `Hitbox`** — the mop ray can hit **any `BasePart`** in the
    model and `SpillResolver` (SharedModules) climbs from the hit part up to the enclosing spill
    Model. A spill's visible puddle is often `CanQuery = false` (the ray would pass through it), so
    a spill **may** carry an optional invisible child `BasePart` named `Hitbox` purely to give the
    ray something to hit — it's excluded from the fade.
- **Flow:** `MopController` (client) drives the clean per-frame while the player **holds click** on
  a spill of the business whose job they hold: each `Heartbeat` it fades that spill's parts'
  `Transparency` toward `MAX_TRANSPARENCY` (0.48) by the mop's **`Power` per second** and grows a
  billboard progress bar over the spill. When the fade completes it hides the spill locally
  (`SpillVisibility`), counts it toward local completion (`JobController` → `JobClient`), and fires
  **`CleanSpill`** to the server. `SpillCleaningService` (server) re-validates (spill resolves,
  belongs to the active job), pays a **flat per-spill reward** (`SPILL_CASH`/`SPILL_XP` = 4/4), and
  records the spill in the player's **`JobServer`** (`markSpillCleaned`, deduped — may complete the
  job). The spill Model is **shared and left intact server-side**; only the cleaning player's client
  hides its copy.
- **Progress persists mid-job, resets on redo.** Releasing click (or looking away) **pauses** a
  spill mid-fade — its progress and its billboard bar stay until the spill finishes or the job
  changes. Fully-mopped spills are hidden; partly-mopped ones are left in place, faded. Re-accepting
  the job (or ending it) resets **every** one of that business's spills back to its authored
  Transparency for the redo — owned by `SpillVisibility`, and `MopController` also restores its own
  fades from the base snapshots it took, so a spill is guaranteed dirty again even if visibility
  tracking misses it.
- **Cleaned-spill tracking lives in the `JobServer`**, so it resets on each accept — redoable and
  re-earnable, exactly like stains.

### `SpillVisibility` (client)
The spill counterpart to `DecalVisibility` (stains). Spills are shared, server-authored Models
replicated to everyone, but a player should only **see and mop** a business's spills while they're
on that business's job. So it **hides every spill by default** (reparented off-world into a
nil-parented holder, which also makes it non-raycastable) and shows a business's spills **only
while it's the active job**, driven by `JobController` off the `ActiveJob` attribute. It also owns
the **redo reset**: showing a business's spills restores every one — fully-mopped (hidden) or
partly-mopped (in place) — to its authored Transparency, snapshotted the first time each spill is
seen. Exposes `getSpillCount(businessId)` for the completion total and
`getActiveVisibleSpills()` (every still-dirty active-job spill — hidden ones are exactly the
fully-mopped ones) — prepared for the remaining-cleanables highlight, though spills aren't wired
into that reveal yet (see below).

### `MopController` (client)
- Detects the mop via the `ToolId` attribute (`"mop"`) and binds `Equipped`/`Activated` (hold to
  fire) / `Deactivated`/`Unequipped`, mirroring the pressure washer. **Mobile** (touch-only) is
  **look-to-clean**: it cleans **continuously while the mop is equipped and a job is active**,
  aiming from the crosshair (`ViewportSize/2`) — no tapping — since hold-to-clean while dragging to
  look is impossible. Exactly like the washer, this is reconciled by a `refreshMobileFiring` helper
  driven by **both** the `Equipped`/`Unequipped` events **and** the `ActiveJob` attribute, so a mop
  already equipped when a fresh job starts fires without a tap and stops the instant the job ends
  (equip alone can't gate it — the mop can stay equipped through the JobSummary). Desktop/console
  keep hold-to-clean.
- Per `Heartbeat` while firing + on a job: raycasts (out to the mop's `Range`, ignoring the
  player's own floating tool), resolves the hit to a spill via `SpillResolver`, and — only for a
  spill of the active business, not already finished this job — advances that spill's fade by
  `Power × dt` and refreshes its billboard bar. Reads `Power`/`Range` **live** from the player's
  DataService `Inventory` (falling back to `ToolConfig.mop`) so tool upgrades take effect at once.
- The billboard bar is **persistent per spill** once started — it does **not** disappear on
  release or look-away, only when the spill finishes (destroyed) or the job changes
  (`clearAllBars`). A short looping mop sound plays only while actively fading a spill.

### Web cleaning (vacuum, implemented)
The **fourth** cleanable kind, alongside walls, stains, and spills. A web is cleaned **exactly like
a stain** (a single server-timed click, not a continuous fade) — the vacuum is a direct mirror of
the broom, just a different tool + folder.
- A cleanable **web** is a **direct child of** a business's `CleanableWebs` folder, at:
  `Workspace.<BusinessesFolderName>.<businessId>.Cleanables.CleanableWebs.<web>`.
  - Unlike a stain (always a `Model` with a `Hitbox`), a web may be authored **either as a single
    `BasePart`** (the web mesh itself is the target) **or as a `Model`** grouping several parts —
    both work. `WebResolver` (SharedModules) climbs from any hit part up to whichever instance sits
    directly in the `CleanableWebs` folder and reads its **`surfaceId`** attribute (lowercase, like
    stains/walls; a number is accepted and normalised to a string), yielding
    `{ businessId, surfaceId, web }`.
  - **Web-authoring gotcha (hitboxes must be Anchored).** A web Model typically pairs a thin
    `Web` mesh with an oversized invisible `Hitbox` part so it's easy to click. That hitbox **must
    be `Anchored = true`** (and `CanQuery = true`, `CanCollide = false`). Authored unanchored with
    no weld, gravity drops it through the world at runtime, leaving only the razor-thin mesh
    clickable — the fix applied to every existing web. Anchoring is safe: `WebVisibility` hides/shows
    webs by reparenting off-world, which preserves an anchored part's CFrame.
- **Flow:** `VacuumController` (client) raycasts on click, and on a valid web (for the business
  whose job it holds) fires **`CleanWeb`** and shows a cosmetic billboard progress bar — its aim ray
  **excludes every business's `CleanableSpills`** so a spill's hitbox can't shadow a web near it.
  `WebCleaningService` (server) validates (active job / vacuum-equipped / one-at-a-time /
  not-already-cleaned-on-this-job), **runs the UseTime timer itself**, re-validates, pays a **flat
  per-web reward** (`WEB_CASH`/`WEB_XP` = 4/4), records the web in the player's **`JobServer`**
  (`markWebCleaned`, deduped — may complete the job), and fires **`WebCleaned`** back to **that**
  client. The web is **shared and left intact server-side**; the cleaning player's client **hides**
  its copy via `WebVisibility`, and re-accepting restores it for the redo. **UseTime** comes from
  the vacuum Item in `ToolConfig` (`vacuum`, slot 4, default 2.5s); both sides read the same
  per-player source so the bar mirrors the server timer.
- **Boundary-click parking (mirrors the broom).** A click on the *next* web that races the previous
  clean's completion callback is parked in `pendingClick` (newest wins) and processed the instant
  the vacuum frees up, rather than dropped — otherwise the client would show a bar and mark the web
  started but no clean would ever run. The client mirrors this with a `startedClean` set +
  `SERVER_CONFIRM_GRACE` window so a rejected click can't brick a web for the rest of the job.
- **Cleaned-web tracking lives in the `JobServer`**, so it resets on each accept — redoable and
  re-earnable, exactly like stains and spills.

### `WebVisibility` (client)
The web counterpart to `DecalVisibility` (stains) / `SpillVisibility` (spills). Webs are shared,
server-authored instances replicated to everyone, but a player should only **see and vacuum** a
business's webs while they're on that business's job. So it **hides every web by default**
(reparented off-world into a nil-parented `HiddenWebs` holder, which also makes it non-raycastable)
and shows a business's webs **only while it's the active job**, driven by `JobController` off the
`ActiveJob` attribute. Because a web may be a `BasePart` **or** a `Model`, it works in `Instance`s
(the direct child of `CleanableWebs`) rather than `Model`s specifically. Reparenting (not
destroying) keeps the shared server instance and its CFrame intact for the redo. Exposes
`getWebCount(businessId)` for the completion total and `getActiveVisibleWebs()` (every still-dirty
active-job web) — prepared for the remaining-cleanables highlight, though webs aren't wired into
that reveal yet (like spills).

### `VacuumController` (client)
Detects the vacuum via the `ToolId` attribute (`"vacuum"`) and binds `Equipped`/`Activated`
(click) / `Unequipped`, mirroring the broom. On click it raycasts (out to the vacuum's `Range`,
read live from the player's DataService `Inventory` so upgrades apply at once, falling back to
`ToolConfig.vacuum`), resolves the hit to a web, and — only for a web of the active business —
fires `CleanWeb` and animates a billboard bar over the web for the same UseTime. The bar is purely
cosmetic (the server owns timing/completion); it tears down early if the web is hidden/removed. The
aim ray excludes the player's own character and every business's spill folders.

### Garbage carrying (implemented)
The **fifth** cleanable kind, and the only one with no tool: the player walks up to a piece of
litter, clicks it, and **carries** it in front of them. Getting rid of it is *Garbage shredding*,
below.

- A piece of **garbage** is a **direct child of** a business's `CleanableGarbage` folder, at:
  `Workspace.<BusinessesFolderName>.<businessId>.Cleanables.CleanableGarbage.<garbage>`.
  - Like a web, it may be a single **`BasePart`** *or* a **`Model`**. `GarbageResolver`
    (SharedModules) climbs from any hit part to the folder's direct child and reads its
    **`SurfaceId`** attribute (capital-S, like spills; a number is normalised to a string),
    yielding `{ businessId, surfaceId, garbage }`, plus `getPosition`/`getParts` helpers both
    sides share.

- **Why garbage can't be a shared instance.** Every other cleanable is one server instance that
  never moves, so each client can simply hide or show its own view of it. Garbage moves — and a
  shared instance has **one position for the whole server**, which means two players (or two
  parties) working the same building would drag each other's pieces around, and one starting a job
  would reset the other's mid-run. So:
  - The **authored pieces are templates**. `GarbageCarryService` pins them at startup (`Anchored`,
    `CanCollide = false`) and never moves them again; their CFrame at that moment is each piece's
    **home**.
  - Every client takes them **off-world** and, when a job starts, **clones** that business's pieces
    back into the very same `CleanableGarbage` folder (`GarbageVisibility`). Cloning them *in
    place* is what keeps `GarbageResolver` — and everything downstream of it — working unchanged.
  - A clone exists on one machine only, so carrying, dropping and resetting it are invisible to
    every other session. **Rebuilding the clones IS the job-start reset**, the same fresh slate
    re-accepting a job gives the stains and webs.

- **Physics, not teleporting.** A carried piece is **dragged** by an `AlignPosition` +
  `AlignOrientation` pair toward a point `GarbageCarryDistance` studs down the crosshair ray,
  keeping its authored tilt and turning with the camera. Dragging rather than writing its `CFrame`
  is what makes the building's collisions apply — shove a piece at a wall and it stops at the wall
  instead of passing through and stranding itself out of bounds. Guards, each learned from a real
  failure:
  - The pull is **finite** (`CARRY_GRAVITIES` = 20× the piece's own weight). An infinitely strong
    constraint beats the collision solver and pushes the piece through whatever it's pressed on.
  - The carry point is **raycast-clamped** to stop `CARRY_SURFACE_BUFFER` short of whatever the aim
    ray hits. Without it, looking down puts the target *underground* and the constraint grinds the
    piece through the floor.
  - `MaxVelocity` is capped at **35**; faster than that, a small part clears a thin floor in a
    single physics step and tunnels through it.
  - A piece that ends up more than `GarbageCarryDistance + 15` studs away (wedged behind geometry
    while the player walks off) is **dropped automatically** rather than towed through the level.
  - Clones sit in a **`CleanableGarbage` collision group**, registered in the place and paired
    non-collidable against `PlayerCollisionService.GROUP` — so garbage collides with the building
    but **never with a character**: it can't shove a player, trap them, or be stood on.

- **Flow.** `GarbageCarryController` (client) raycasts each frame; a free piece of the active job's
  garbage within `GarbageHoverRange` gets a **white `Highlight`** (`AlwaysOnTop` — an occluded
  outline on a pale model is nearly invisible). A click sends **`CarryGarbage`** with the
  `surfaceId` (out to the longer `GarbagePickupRange`), or `nil` to let go.
  `GarbageCarryService` validates the active job, that no **party member** already holds that
  `surfaceId`, and the range — measured against the last position that *session* reported, falling
  back to the authored home — then publishes **`GarbageCarry`** `(carrier, surfaceId?)` to the
  session. Nothing moves until that confirmation arrives.
- **Party sharing.** A clone can't replicate itself, so the carrier streams its piece's CFrame on
  **`GarbageMove`** (20 Hz, throttled by distance) and the server forwards it to the **other**
  members of that session only. They anchor their own clone of that `surfaceId` while it's in
  someone else's hands and drive it from the relay, then release it to local physics on the drop —
  so a dropped piece can settle a stud or two differently per screen, the accepted cost of local
  simulation.
- **Settle report.** The relay stops the instant the carrier lets go, so the server would still
  believe the piece is up where it was released — and refuse a legitimate re-grab from beside where
  it landed. The client therefore sends **one** final `GarbageMove` 2s after its own drop, which
  the server accepts only from that piece's **last carrier**, and only while nobody else holds it.
- **Hands-full.** Picking up **unequips** any held tool, and equipping a tool **drops** the piece —
  both directions, so the carry and the cleaning tools can never overlap. A carry is also dropped
  automatically on job end/switch, respawn/death, and disconnect.
- **Idle reset.** A piece untouched for `GarbageResetSeconds` (**60s**) returns to its authored
  home (velocity zeroed, or it arrives still rolling). Client-side, since the pieces are local.
- **Session state** lives in a **weak-keyed** table on the shared `JobServer`, so a finished
  session's carry state is collected with it — nothing to sweep up.

### `GarbageVisibility` (client)
The garbage counterpart to `DecalVisibility` / `SpillVisibility` / `WebVisibility`, but it does
more than show and hide. It scans for authored pieces, records each one's **home CFrame** and
business, counts them (`getGarbageCount(businessId)` feeds the completion total), and moves every
one **off-world** into a nil-parented `AuthoredGarbage` holder — they are never seen. Then
`setActiveBusiness(businessId)`, driven by `JobController` off `ActiveJob`, **destroys the previous
job's clones and builds this job's** at their authored positions, each unanchored, collidable and in
the garbage collision group. Clones are marked with a `LocalGarbageClone` attribute so the scan
never mistakes one for an authored piece, and a piece that replicates in *after* a job has started
still gets its clone. Exposes `getPiece(surfaceId)` / `getPieces()` / `getHome(surfaceId)` for the
carry, `hideOne(surfaceId)` (which, unlike every other cleanable kind, can simply **destroy** the
clone, since it's ours), and `takePiece(surfaceId)` — hand the clone over *without* destroying it,
used by the shredder, which needs the piece to stay in the world for its animation while being
untouchable by the carry, the hover and the idle reset.

### Garbage shredding (implemented)
How a piece of garbage is actually **cleaned**: the player carries it into the business's
**shredder** and it's chewed up. This is the disposal half of the garbage mechanic; the carry half
is above.

- **Authoring.** Every business with cleanable garbage authors one shredder model **directly in the
  building** (not under `Cleanables` — it isn't itself a cleanable):
  `Workspace.<BusinessesFolderName>.<businessId>.Shredder`, holding three invisible parts —
  **`Hitbox`** (touch this with a piece to feed it in), **`p1`** (the mouth) and **`p2`** (inside
  the machine). `ShredderResolver` (SharedModules) resolves the set for a `businessId`; a business
  with no garbage simply doesn't author one.

- **Who notices the touch.** Garbage is the one cleanable that isn't a shared instance, so the
  collision only exists on the machine simulating the piece — normally the carrier, whose clone is
  unanchored (a party member's copy is *anchored* while someone else holds it, so it can't fire
  `Touched` and doesn't need to). Their client fires **`ShredGarbage`** with the `surfaceId`.

- **Validation.** `GarbageShredService` checks the player is on that business's job, the `surfaceId`
  names a real authored piece of it (`GarbageCarryService.isPiece`), the piece isn't already cleaned
  on this job, and the building actually has a shredder. It also keeps a **weak-keyed, per-session**
  set of pieces currently going through the machine, which is what swallows the duplicate reports a
  party can produce (one per member's clone) and any repeat during the animation. Then it takes the
  piece out of whoever's hands it was in (`GarbageCarryService.dropPiece`).

- **What everyone sees.** No clone can be moved from the server, so the confirmation
  (**`GarbageCleaned`**, carrying just the `surfaceId`) goes to **every member of the session** and
  each client animates its **own** clone. That's what makes a party watch the same piece shredded.

- **The animation** (`GarbageShredController`, client). The piece is taken out of
  `GarbageVisibility` (`takePiece`) so nothing can carry, hover or reset something already in the
  machine, then **frozen**: its carry constraints stripped by name, every part `Anchored` and
  `CanCollide`/`CanTouch`/`CanQuery` off, velocities zeroed. Its pivot is then driven off
  `Heartbeat` (not a `Tween` — a `Model` has no tweenable CFrame, and the shake has to be
  re-randomised every frame) through three beats from `CleaningConfig`:
  **`GarbageShredEntrySeconds`** (0.3s) move to `p1` → **`GarbageShredHoldSeconds`** (0.45s) hold →
  **`GarbageShredDropSeconds`** (2s) drag down to `p2` with a per-frame jitter, then destroyed. The
  jitter is **side to side** (±0.22 studs along the piece's own X), with only a hint of vertical
  (much more fights the descent and just reads as glitching) and nothing in/out, plus a token ±1.2°
  wobble.

- **Sound and debris cover the descent only** — the beat where the piece is actually being chewed,
  not the approach or the pause at the mouth.
  - **`ShredderSFX`** is cut off the instant the piece is gone — the machine is only ever heard
    chewing something — and starts **`GarbageShredSoundLeadSeconds`** (0.3s) *before* the drop, i.e.
    partway through the hold: the file opens on the machine spinning up, so starting it dead on the
    drop puts the bite after the piece is already moving. (Clamped to the hold's own length, so
    shortening the hold below the lead just starts it at the top of the hold.) It's played
    **positionally** out of the hitbox (`SoundManager.playAt`), so it fades with distance and a
    member across the building hears it from where it is.
  - **`VfxManager.shredDebris`** — a shower of **yellow** flecks thrown out in every direction and
    yanked down hard, riding the piece as it goes. A *mix* of yellows needs **one emitter per
    colour** (a `ParticleEmitter`'s `ColorSequence` varies a particle over its own lifetime, not from
    particle to particle), so there are six, running from almost-white through gold and amber to a
    dark bronze — the dark end is what stops it reading as one flat yellow blob. The emission rate is
    therefore **per colour**: lengthening the palette thickens the shower unless the rate is divided
    to match. They're solid **squares**, not
    the fuzzy star a `ParticleEmitter` defaults to — chips, not sparkles — drawn from a small
    pure-white opaque texture. That whiteness is load-bearing: a particle's `Color` *multiplies* its
    texture, so pure white reproduces each palette colour exactly, while a dark or semi-transparent
    source couldn't be tinted bright at all. The emitter is a throwaway
    invisible part of ours, not an attachment on the garbage — destroying the piece would take every
    fleck still in the air with it, and the shower has to outlive it. Unlike the rest of `VfxManager`
    it returns a **handle** (`move`/`stop`) rather than being fire-and-forget, since it runs for as
    long as the machine does.

- **When it counts.** The server waits out **the same total** (2.75s) before paying the reward
  (4 XP / 4 Cash, matching a web) and calling `JobServer.markGarbageCleaned`, so the completion bar
  ticks as the piece *disappears* rather than as it starts moving — and the piece that completes a
  job doesn't end the job out from under its own animation. The client counts it toward its own bar
  at the same moment (`JobController.onGarbageCleaned`, keyed by `surfaceId`).

- **Job ends mid-animation.** An in-flight piece is nobody's but the controller's, so it tracks them
  and destroys anything still animating when `ActiveJob` changes.

### Reveal remaining cleanables (implemented)
A client-only assist that flashes a neon-yellow glow over everything the player still has left
to clean on their active job. **Purely cosmetic** — it reads existing client state and touches
no server state or remotes.
- **Trigger:** the **R** key **or** the on-screen **`ScreenGui.HighlightButton`** (an
  `ImageButton`), both routed through `MissingHighlightController`. The button is shown **only
  while a job is active** (off `ActiveJob`, like the rest of the HUD) and re-binds on each
  respawn.
- **Walls glow per-pixel.** `SurfaceManager.setWallsGlow(true)` calls `CleanableSurface.setGlow`
  on every built wall. `setGlow` recolors the still-dirty pixels of the wall's **own dirt image**
  toward neon yellow (blend `0.85`) and uploads that to the existing dirt decal — **no second
  decal**, so nothing z-fights (two coplanar decals used to render unreliably: some walls showed
  no glow, others lit up whole). The real dirt (`self.pixels`) is untouched; the recolored
  `glowBuffer` has its alpha erased in lockstep with the dirt inside `stamp`, so the glow
  **shrinks live as the player cleans**, and disabling it (or finishing the wall) re-uploads the
  plain dirt. Only the not-yet-cleaned pixels light up.
- **Stains glow whole.** Stains have no partial state, so `MissingHighlightController` switches
  each visible stain part (from `DecalVisibility.getActiveVisibleStains`, skipping the invisible
  `Hitbox`) to `Material = Neon`, neon yellow, **0.55 transparency**, snapshotting and restoring
  each part's original material/color/transparency exactly.
- **Spills and webs are not yet highlighted.** `SpillVisibility.getActiveVisibleSpills()` and
  `WebVisibility.getActiveVisibleWebs()` both exist for this (the still-dirty active-job
  spills/webs), but `MissingHighlightController` currently glows only walls and stains — wiring
  spills and webs into the reveal is a small, pending follow-up.
- **Duration + cooldown.** The glow lingers `REVEAL_DURATION` (**8s**) then clears itself (a
  `revealToken` disarms superseded expiry timers). Re-triggering is gated by the **same
  duration** — a new reveal is ignored until the current one runs out — since each reveal
  rebuilds every wall's glow overlay (new `EditableImage`s) and spamming it would churn them and
  hitch the game. The cooldown resets on job change so a fresh job is immediately ready. Ending
  or switching a job drops the glow.

### Tool
- The **Pressure Washer**, **Broom**, **Mop**, and **Vacuum** `Tool`s live in
  **`ReplicatedStorage.Items`** (authored in Studio; `StarterPack` is empty). Each has a `Handle`
  and a `ToolId` attribute (`"pressureWasher"` / `"startingBroom"` / `"mop"` / `"vacuum"`) that ties
  it to its inventory Item (`UniqueID`) and is used to bind its controller. The mop sits in hotbar
  **slot 3** (`ToolConfig.mop.SlotNumber`) and uses **`Power`** as its fade rate (Transparency/sec)
  plus `Range`; both are upgradable (`UpgradePower`/`UpgradeRange`). The vacuum sits in **slot 4**
  (`ToolConfig.vacuum.SlotNumber`) and, like the broom, uses **`UseTime`** (server-timed, default
  2.5s) + `Range`, both upgradable (`UpgradeUseTime`/`UpgradeRange`).
- **`ToolService`** (server) grants tools: on each spawn it clones every owned + `Unlocked`
  inventory item's `Tool` into the player's Backpack (matched by `ToolId`), idempotently,
  and re-grants when the inventory gains a new item.
- **`InventoryController`** (client) is the custom hotbar, replacing Roblox's default
  Backpack UI (which it disables via `SetCoreGuiEnabled`). The HUD `ScreenGui.Inventory`
  frame holds `ImageButton1..5`; a button is shown only if the player owns an item whose
  `SlotNumber` matches it. Clicking a button — or pressing that number key — equips that
  slot's Tool with `Humanoid:EquipTool`. It only ever equips (never `UnequipTools`), so a
  slot press **never unequips**: the already-equipped slot is a no-op.
- **Tied to the job lifecycle** (off the `ActiveJob` attribute, like the rest of the HUD):
  the inventory is **hidden unless the player holds a job**. On job **start** the frame
  appears and **slot 1 is auto-equipped**; on job **end** the frame hides and any held tool
  is unequipped (`Humanoid:UnequipTools`). Re-binds to the fresh `Inventory` frame on each
  respawn, like the other HUD controllers.

and then watches `DescendantAdded`, so **every** `GuiButton` — including UI cloned in later (the

(`UiAnimations.hoverGrowInGrid`) widens the grid's `CellPadding` by exactly how far the grown edge
reaches, so the row-neighbour is pushed aside and the gap stays constant; the left-edge button
additionally tweens the frame's `UIPadding.PaddingLeft` so it grows *into* that new room rather
than off the screen edge. (Skipping by **name** is deliberate: it's deterministic, where a
first-one-wins guard would race the sweep against the controller's bind.) The stacked clusters also
open up via `UiAnimations.spreadStackOnHover`: hovering a button in one pushes the others away from
it -- clusters above slide up, those below slide down, the hovered one holds -- so they don't
crowd. `JobUiController` hides the whole
`Button1` frame — not just `JobButton` — while a job is active, so no HUD buttons show mid-job. `UiPreloader` warms these assets' images up
front (via `ContentProvider:PreloadAsync` on the `StarterGui` templates, in a background task)
so they don't first render blurry.

- **Shredders only exist in `gasStation`.** Garbage disposal is built end to end (see *Garbage

- **Progression** — the loop is now closed end to end: **business unlocking by Level**

# Design Vision & Principles

Forward-looking guidance. Still authoritative for *how* new systems should be built,
even where the feature itself isn't implemented yet.

## Gameplay loop (target)

1. Player spawns on their own plot (home base) with starting tools.
2. Player accepts a job from the job board → teleported to that shared business.
3. On job start the hotbar appears with slot 1 auto-equipped; the player swaps tools
   (button / number key) and cleans the business's surfaces / stains, earning Cash + XP
   per clean (per-session — nothing is saved). The hotbar hides again when the job ends.
4. Player reaches Levels to **unlock** more businesses (implemented, permanent — via each
   business's `RequiredLevel`, plus its `RequiredItems` tool gate), and spends Cash on their
   **plot's purchase buttons** (implemented via `PlotButtonService`) to reveal **Spawnables**
   that passively generate **Gems**.
5. Player spends those **Gems** on the two sinks: the **upgrades shop** (implemented via
   `ShopService` — unlock + level up tools) and **skills** (implemented via `SkillsService` —
   permanent +5%/level passives), which make the next loop faster and richer.
6. Repeat against a steadily expanding catalog of businesses, tools, and plot unlockables.

## Replication model (target)

- **Pixel erasing stays client-only, visual, never saved or replicated.**
- **Garbage goes further: the objects themselves are client-only.** A moving cleanable can't be one
  shared instance without one session's carry disturbing another's, so each client works with local
  **clones** and only the *carry state* (who holds which `surfaceId`) and a per-session position
  **relay** cross the wire. See *Garbage carrying*.
- Cleaning is **per-session**: leaving (or switching jobs) loses all cleaning progress.
  Nothing about cleaned walls/stains is saved — only the business `Unlocked` flag is.

## Data / Persistence — DataService

The game uses the **DataService** package (`leifstout/dataservice`) for **all player
data**, paired with the `DataTemplate` module which defines the saved-data shape.

**Rules:**
- Route **all player data changes through DataService**; prefer its methods
  (get/set/update, array ops, change signals) over hand-rolled handling.
- Let DataService's **built-in replication** keep clients in sync — no parallel path.
- **Server-authoritative:** clients send validated requests; the server validates
  before writing.

### Saved-data shape (`DataTemplate`)
`src/ReplicatedStorage/SharedModules/DataTemplate.luau`:

- `Cash: number` — primary currency, earned from jobs and spent on the **plot's purchase
  buttons**. (Tool purchases/upgrades and skills are **Gems**, not Cash.)
- `Gems: number` — secondary currency, generated per-second by unlocked plot spawnables (the
  worker + buff model); awarded via `ProgressionService.awardGems` (boosted by `Hoarding`). Spent
  on the **upgrades shop** (`ShopService`) and **skills** (`SkillsService`).
- `Level: { CurrentLevel: number, XP: number }` — `XP` is progress **within** the current level,
  counting up toward `Leveling.xpForLevel(CurrentLevel)` and rolling over on level-up (the server
  replaces the whole `Level` table on each award, so one changed signal covers both fields).
- `Skills: { [string]: number }` — level per skill, keyed by `SkillName` (`RadiusMaster`,
  `Speedy`, `Inteligence`, `Greed`, `Hoarding`), each `0`..`SkillsConfig.MAX_LEVEL`. Bought with
  Gems; see *Skills*.
- `Settings: { MusicVolume: number, SFXVolume: number, HidePlayers: boolean }` — persisted client
  preferences (volumes default to `0.5`, `HidePlayers` off). Written only via `UpdateSetting`,
  through `SettingsService`'s per-key sanitizers; see *Settings*.
- `BusinessList: { [string]: Business }` keyed by `UniqueID`. Each `Business`:
  `BaseReward`, `XpReward`, `Unlocked`, `Name`, `UniqueID`, `Completions`, and optional
  catalog-only `DecalWeight?` / `SpillWeight?` / `WebWeight?` / `GarbageWeight?` / `RequiredLevel?` /
  `RequiredItems?` (the four weights are the completion-bar slices stains/spills/webs/garbage own —
  default `CleaningConfig.DefaultDecalWeight`/`DefaultSpillWeight`/`DefaultWebWeight`/
  `DefaultGarbageWeight`; walls get the rest, see `CompletionWeights`). **`Unlocked`** gates whether
  the player may accept that business's job (resolved per player by `BusinessService`);
  **`RequiredLevel`** (catalog, `BusinessConfig`) is the level needed to unlock/accept it;
  **`RequiredItems`** (catalog) is a list of tool `UniqueID`s the player must have `Unlocked` —
  a gate **on top of** `RequiredLevel`, not a replacement (both must pass). Its order drives the
  board's requirement icons (first entry → `Item1`), capped at **5** (the board authors that many
  slots); omitted means the business needs no tools. `Completions` is a
  lifetime tally bumped on each full completion, which also drives **job mastery** (stars + a
  linear XP boost, +5% of base per star). Per-clean *surface* state is **not** stored (jobs are per-session).
- `Inventory: { [string]: Item }` keyed by `UniqueID`. Each `Item`: `Name`, `Equipped`,
  `Unlocked`, `Cost`, `UniqueID`, and optional `Range?` (max cleaning distance, studs),
  `Power?`, `UseTime?` (broom seconds-per-stain), `Radius?` (washer brush radius),
  `SlotNumber?`, the catalog-only `Image?` (icon shown wherever the tool appears as a
  requirement), and the upgrade tuning `BaseUpgradeCost?` / `UpgradeRange?` / `UpgradeRadius?` /
  `UpgradeUseTime?` (see `ItemUpgrades`). **`SlotNumber`** places the item in the custom hotbar: it maps to
  `Inventory.ImageButton{N}` and the matching number key (see `InventoryController`).
  **`Power`** has two roles depending on the tool. For the **mop** it's the **spill fade rate**
  (Transparency added per second while mopping; `ToolConfig.mop.Power` default `0.4`, upgraded by
  `UpgradePower`) — read live by `MopController`, so it's a real, enforced stat today. For other
  tools `Power` is (still) a planned **tool tier** that will gate **which surface types a tool can
  clean** (clean only if `Power` ≥ the surface's required power) — defined in `ToolConfig`, not yet
  enforced in that role.
- `ShopBoosts: { CashMultiplier: number, GemMultiplier: number, SpeedBonus: number }` — the
  **permanent** Robux store perks (multipliers default `1`, speed bonus `0`). Read through
  `ShopPerks`; applied by `ProgressionService` (cash/gem awards) and by `SkillsService` /
  `JobServer` (walk speed, added after the `Speedy` multiplier). See *Robux store*.
- `TutorialComplete: boolean` — whether the player **finished** onboarding, set when the last step
  ends. See *Tutorial resume* for the older meaning this flag used to carry.
- `TutorialStep: number` — the step a partway-through run resumes at; `0` = never started (and what
  it returns to on finish). The next join doesn't always re-enter this exact step —
  `TutorialConfig.resumeStep` decides. See *Tutorial resume*.
- `FunnelProgress: { PlotCompletion: number, JobsUnlocked: number }` — highest step already reported
  into each progression funnel, so a rejoin can't re-report it. Analytics bookkeeping only; nothing
  in the game reads it. See *Analytics funnels*.
- `PlotButtonsBought: { [string]: boolean }` — set of plot **purchase buttons** the player has
  bought (e.g. `{ Button1 = true }`). Layout-agnostic (button names are the same on every plot),
  so `PlotButtonService` replays it onto whichever plot the player is assigned. Empty on a fresh
  player → only `Button1` visible. See *Plot purchase progression*.

**Why string-id maps, not Instance refs:** saved data is JSON-only (no Instances), and
an Instance is a new object every session anyway. A stable `SurfaceId` string survives
save/load and a `{[id]: true}` map gives O(1) membership, dedupe, and clean per-key
writes via DataService's path API.

## EditableImage constraints

- **Max 1024×1024**, **not resizable** after creation (current overlays are 512×512).
- **One EditableImage update per frame per client** — prefer **fewer/larger** surfaces.
- **Memory-expensive:** only the **active business** should hold live editable images;
  completed/distant businesses should use static textures.

## StreamingEnabled

`Workspace.StreamingEnabled` is **on**. The shared business buildings are `Model`s, and each
cleanable kind attaches per-client, non-replicated visuals to that shared geometry — the wall
overlay is a `Decal` + `EditableImage` parented to the wall part; the mop fade mutates the spill
parts' Transparency in place.

- **Business Models are pinned `Persistent`.** `JobService.init` sets every
  `Workspace.Businesses` child (and any added later) to `ModelStreamingMode.Persistent`, so the
  buildings are always fully loaded on every client and **never stream out**. This is a real fix,
  not a target: without it a wall part could be culled mid-job while the player was cleaning it,
  taking its client-side overlay `Decal` with it — the wall visually went **blank** even though the
  server's `JobServer` completion tracking was untouched, so the player kept getting paid for a wall
  they could no longer see (same failure mode for a mid-fade spill's Transparency). Persistent
  removes that whole class of streaming despawn.
- Even so, cleaning code **must not assume surfaces are loaded** — wait for instances and handle
  `nil`. (`SurfaceManager`'s `ChildAdded` watch + budgeted queue and `SpillVisibility`'s
  `DescendantAdded` scan already cover stream-in / late replication.)
- A player only cleans the **shared business of their active job**, which they were just
  teleported into and which is Persistent, so it's reliably present.

## Architecture — entry points & service modules

The entire game runs from **exactly two executing scripts**:

- **One server entry point** — `ServerScriptService/Main.server.luau`.
- **One client entry point** — `StarterPlayerScripts/Main.client.luau`.

**No other Script or LocalScript runs on its own.** Everything else is a ModuleScript.
The two Main scripts do nothing but **require and initialize service modules** in order.

### Service modules
- Treat every system as a **service**: a self-contained module owning one domain
  (e.g. `CleaningService`, `SurfaceManager`, `InventoryManager`, future
  `BusinessManager`, `UnlockManager`).
- Each exposes an **`init` function** that wires it up (connect events, build state,
  cache refs). The relevant Main calls each `init` once, in dependency order. A service
  does nothing until `init` runs.
- Services expose a clear **public API** and keep internals private. Server and client
  services are separate modules; shared logic/types/config live in `SharedModules`.

```
Main.server.luau         requires + init: DataService, CleaningService, (later) InventoryManager, ...
Main.client.luau         requires + init: DataService, SurfaceManager, PressureWasherController, (later) UI, ...
```

### Build reusable systems
A priority, not a nicety — the catalog grows continuously:
- A service handles a **whole category** (all tools, all businesses), data-driven — not
  one hardcoded instance. Adding content = new data + config (+ a behavior handler keyed
  by `UniqueID` if needed), with no new top-level scripts and minimal Main edits.
- Prefer composition and shared helpers over duplication.
- Keep services decoupled: communicate through public APIs / signals, not internals.

## Code standards

- **Typing:** strict Luau (`--!strict`) throughout. (`CleanableSurface` is `--!nonstrict`
  on purpose — the EditableImage/Content APIs aren't fully covered by the type solver.)
- **Structure by shape of data:**
  - **Classes** (OOP, metatables) for many-instance stateful objects (a cleanable
    surface, an equipped tool instance).
  - **Modules/singletons** for systems that exist once (controllers, managers).
  - **Plain typed tables** for pure data (templates, configs).
- **Extensibility:** new content = new data + config + (if needed) a behavior handler
  keyed by `UniqueID`. No core rewrites.
- **Naming:** `PascalCase` for types/classes/modules; `camelCase` for
  variables/functions/params; match existing `DataTemplate` field style.

## Rojo / project structure

Sync map is in `default.project.json`.

```
src/
  ReplicatedStorage/
    SharedModules/   -> ReplicatedStorage.SharedModules   (DataTemplate, configs, shared types)
    Remotes/         -> ReplicatedStorage.Remotes         (RemoteEvents/Functions)
  ServerScriptService/
    Main.server.luau -> ServerScriptService.Main          (server entry point)
    Modules/         -> ServerScriptService.Modules        (server systems)
  StarterPlayer/
    StarterPlayerScripts/      -> client entry point + client modules
    StarterCharacterScripts/   -> per-character client scripts
Packages/            -> ReplicatedStorage.Packages         (Wally deps, incl. DataService)
```

- **Wally** manages dependencies (`wally.toml`); `DataService` lives in `Packages`.
- **All server module scripts live in `ServerScriptService/Modules`**; the only server
  Script outside it is `Main.server.luau`.
- Shared types/configs go in `SharedModules` (one source of truth for client + server).
- **Workspace, ReplicatedStorage.Items, and StarterGui are not Rojo-mounted** — physical
  instances (cleanable parts, the `Tool`s, the HUD `ScreenGui`) are authored directly in the
  Studio place. `StarterPack` is empty; tools are granted from `ReplicatedStorage.Items` by
  `ToolService`.
- Client/server boundaries communicate via `ReplicatedStorage/Remotes`; all state
  mutation requests are server-validated.
